# 全体再統合 運用仕様書

## 1. 目的

全体再統合は、機能追加や局所修正によって分散・重複したUI、操作、状態管理、保存、同期の処理を整理し、同じ役割を持つ処理を共通基盤へ戻す作業である。

単なるコード削減や見た目の統一ではなく、次を同時に達成する。

- 現在利用できる機能を保全する
- モード間の操作感と表示を統一する
- 重複実装と競合するイベント処理を解消する
- 修正箇所を一意にし、次回以降の変更を速く安全にする
- 古い補修レイヤーを検証後に読み込み対象から外す
- PC版とAndroid版の差異を意図したものだけにする

## 2. 最上位の保全原則

全体再統合によって、現在利用できる機能、保存データ、操作方法を意図せず失わせてはならない。

機能の削除、操作変更、データ形式変更が必要な場合は、機能保全表へ明記し、実装前にユーザーの確認を得る。整理の都合だけで機能を削除してはならない。

以下を必須とする。

1. 作業開始時のmainコミットを復元基準点として記録する
2. 現行機能をコード、Git履歴、実画面から棚卸しする
3. 各機能の移行先と検証方法を機能保全表へ記録する
4. 新処理の検証前に旧処理を削除しない
5. データ形式を維持するか、自動移行と後方互換を用意する
6. 一度に全処理を置換せず、共通機能単位で段階移行する
7. 各段階で構文、データ、PC、Android実機の回帰確認を行う
8. 全項目の保全確認後にのみ全体再統合完了版を公開する

## 3. 禁止事項

- 再統合と無関係な新機能を同じ変更へ混在させない
- 動作している旧処理を、代替処理の検証前に削除しない
- 見つけた未使用らしい機能を確認なしに削除しない
- 保存済みデータを読み取れなくする変更を行わない
- モード固有ファイルへ共通操作を新たに複製しない
- 複数のスクリプトから同じグローバル関数を無計画に上書きしない
- 実機依存の操作をPCブラウザ確認だけで完了扱いにしない

## 4. バージョン運用

バージョンは `0.12.121` のように `大.中.小` として扱う。

| 変更 | 例 | 必須処理 |
|---|---|---|
| 小規模修正 | `0.12.121` → `0.12.122` | 通常の影響確認 |
| 機能群追加・構造変更 | `0.12.x` → `0.13.0` | 全体再統合判定、機能保全表、回帰確認 |
| 正式版・非互換級変更 | `0.x` → `1.0` | 全体再統合、データ移行検証、完全回帰確認 |

中央の桁を変更する前に、必ず全体再統合判定を実行する。全コードの再統合が不要と判断した場合も、判定結果と理由を今回用の実行記録へ残す。

全体再統合中の段階的な修正は小バージョンで管理し、機能保全表の全項目が検証済みになった時点で中央の桁を上げる。

## 5. 全体再統合の実施判定

次のいずれかに該当する場合、中央の桁を上げるかどうかにかかわらず全体再統合判定を行う。

- 新しいモードを追加した
- 同じ操作を2画面以上へ個別実装した
- 同じ不具合を複数ファイルで修正した
- 既存の共通機能と似た処理を新しく作った
- 同じ画面、保存、同期、遷移関数を複数スクリプトから上書きしている
- 前回の全体再統合から、読み込み対象のUXファイルが5本以上増えた
- 局所修正による別の不具合が繰り返された
- 修正箇所の特定や実機検証に以前より時間がかかる
- モード間でスワイプ、並べ替え、角丸、色、余白などに差が出た
- Service Workerの読み込み順やキャッシュ更新が複雑化した

## 6. 実行資料

全体再統合では、毎回次の実行資料を作る。

### 6.1 機能保全表

現在の全機能について、以下を記録する。

- モード・画面
- 現行機能と操作
- PC／Androidの対象
- 現在の実装所有者
- 移行先の共通基盤または固有処理
- 現行確認、移行先確定、移行済み、検証済み、旧処理削除済みの状態
- 検証方法

### 6.2 重複・競合一覧

同じ役割を持つCSS、イベント、保存、同期、画面遷移、ダイアログ、固定UIを抽出する。

### 6.3 診断ログ取得指示

診断ログの項目は固定しない。変更対象と影響範囲を調査した後、その回に必要な操作単位で取得指示を作成する。

各指示には次を含める。

- ログの目的
- 開始する画面と状態
- 操作手順
- 成功時に見える挙動
- 記録を停止する位置
- 補足メモへ入力する文言

診断ログが不要な変更では取得しない。見た目の確認には診断ログではなく実画面確認を用いる。

## 7. 標準実行手順

1. 基準点を記録する
2. 現在の読み込み対象ファイルと全画面を棚卸しする
3. 機能保全表を作る
4. 重複・競合一覧を作る
5. 共通化の境界と移行順を決める
6. 必要な診断ログをユーザーへ具体的に指示する
7. 共通基盤を既存処理と並存できる形で追加する
8. 1モードずつ共通基盤へ移行する
9. 各移行後に機能保全表と照合する
10. 全利用箇所の検証後に旧処理を外す
11. PCブラウザとAndroid実機で完全回帰確認する
12. 機能保全表を完了状態に更新する
13. 中央のバージョンを上げて公開する

## 8. 共通基盤へ置くもの

複数モードで使用する次の処理は、原則として共通基盤が所有する。

- カードの左スワイプ削除と右スワイプ複製
- スワイプボタンの形、色、幅、角丸、開閉アニメーション
- 長押し開始、ドラッグ中表示、キャンセル
- 挿入位置の前後ライン
- 画面上下端の段階的な自動スクロール
- 並べ替え確定と並べ替え後の表示
- 削除アニメーション
- 操作メニューの基本形
- 下部ナビゲーションと固定操作UIの積み上げ位置
- 保存後の画面更新と入力フォーカス維持

各モードは、対象要素、ID、削除、複製、並べ替え後の保存など、モード固有の処理だけを共通基盤へ渡す。

## 9. データと同期の保全

以下は再統合中も維持する。

- ローカル保存済みのルーティン、種目、タスク、履歴、予定、レシピ
- Dropboxの `data.json` とメディアファイル
- PCとAndroid間の同期
- 競合判定と単一デバイス編集ロック
- 一時停止中と実行中のタイマー復元
- 既存画像パスとメディアキャッシュ

同期用データに項目を追加する場合、項目がない旧データも読み込める既定値を用意する。

## 10. 検証区分

| 区分 | 主な対象 |
|---|---|
| 静的確認 | 構文、読み込み順、重複ID、不要参照 |
| PCブラウザ | クリック、入力、ドラッグ、画面遷移、保存 |
| Android実機 | スワイプ、長押し、自動スクロール、戻るジェスチャー、キーボード |
| 同期 | Dropbox取得、保存、競合、ロック、メディア |
| タイマー | カウント、音、停止、再開、逆サイド、完了、PiP |
| データ | 既存データ読込、更新後保存、再起動復元 |

## 11. 完了条件

次をすべて満たした場合のみ全体再統合を完了とする。

- 機能保全表の必須項目がすべて検証済み
- 共通化対象にモード固有の重複実装が残っていない
- 古い処理を外した後も全回帰確認が通る
- 既存データとDropbox同期が維持される
- PC版とAndroid版で重大な差異がない
- 復元基準点と最終コミットが実行記録に残っている
- 完了版として中央のバージョンを更新している

## 12. 今後の変更時の規則

新しい機能を実装する前に、同じ役割の共通基盤がないか確認する。存在する場合は共通基盤を拡張し、モード固有の類似処理を追加しない。

共通基盤では対応できない場合は、理由と将来の共通化可能性を変更記録へ残す。全体再統合の判定条件に達した場合は、本仕様書に従って次の実行記録を作る。
